## 2. Go 语言（34 项）

### 2.1 基础与类型

- ⬜ **变量声明**：`:=` 短声明 vs `var`；包级变量初始化顺序
- ⬜ **零值**：各类型零值；nil slice vs 空 slice JSON 差异
- ⬜ **string 与 []byte**：不可变、共享底层、转换成本
- ⬜ **rune 与 UTF-8**：遍历字符串、`range` 得到 rune
- ⬜ **数组 vs 切片**：值拷贝 vs 切片头；`append` 扩容由运行时决定，小容量常快速增长、大容量逐步放缓，不能死背固定 2 倍
- ⬜ **map**：非线程安全；`delete`；遍历时删除规则
- ⬜ **new vs make**：`new(T)` 分配零值返回 `*T`；`make` 只用于 slice/map/chan，返回初始化好的 T 本身（代码实证见 §2.4.3）
- ⬜ **方法集与接收者**：值接收者 vs 指针接收者；`T` 与 `*T` 方法集不同，决定能否满足接口（代码实证见 §2.4.3）
- ⬜ **struct 嵌入**：Promotion；与方法集
- ⬜ **interface**：隐式实现；nil interface 陷阱——接口值内部存 `(动态类型, 动态值)` 两个字段，只有两者都为 nil 时接口才 `== nil`；把一个值为 nil 的具体类型指针赋给接口后，动态类型非 nil、动态值为 nil，整个接口 `!= nil`，这就是「typed nil」坑
- ⬜ **type switch / assertion**：安全断言 `ok` 模式
- ⬜ **defer**：LIFO；执行时机在「return 先给返回值赋值」**之后**、函数真正返回之前——所以 defer 能改**命名**返回值，改不了匿名返回值
- ⬜ **error 与 panic**：错误包装 `%w`；何时 panic vs error
- ⬜ **iota 与 const**：枚举位掩码

### 2.2 并发与内存

- ⬜ **goroutine**：初始栈很小（最小 2KB，Go 1.19+ 会按历史平均用量自适应决定初始大小），按需增长/收缩；对比线程 MB 级固定栈
- ⬜ **GMP 模型**：G/M/P 职责；work stealing 一句话。深挖程度看岗位：校招/初级岗（大厂 P6 以下，此处 P 是职级、不是 GMP 里的 Processor）讲清三者职责即可；高级岗（P7+）需补充 work stealing、sysmon 监控线程、goroutine 陷入 syscall 时 M 与 P 的交接（handoff）等细节
- ⬜ **for range 循环变量**：Go 1.22 起每次迭代都是新变量，旧版闭包共享陷阱；语义由 go.mod 的 `go` 指令版本决定（代码实证见 §2.4.1）
- ⬜ **channel**：无缓冲同步 vs 有缓冲；关闭后 receive 先取尽缓冲中剩余值、之后立即返回零值（`ok` 为 false）；向已关闭 channel send 则 panic: send on closed channel（可 recover 的普通 panic，代码实证见 §2.4.2）
- ⬜ **select**：随机公平；`default` 非阻塞
- ⬜ **sync.Mutex / RWMutex**：不可重入；defer Unlock
- ⬜ **sync.WaitGroup**：Add 要在 go 语句前；Done 配对；Go 1.25+ 可用 `wg.Go(f)` 一步替代 Add/Done（见 §2.4.1 末尾）
- ⬜ **sync.Once / sync.Map / atomic**：只执行一次、读多写少专用映射、无锁数值操作；与 Mutex 的取舍（代码实证见 §2.4.4）
- ⬜ **context**：取消传播；`WithTimeout` 在 HTTP 中的用法
- ⬜ **竞态**：`-race`；map 并发写触发 `fatal error: concurrent map writes`，是运行时 throw，**不能被 recover 捕获**（区别于可 recover 的普通 panic，代码实证见 §2.4.2）
- ⬜ **内存模型与 happens-before**：channel、锁建立同步关系；无同步的跨 goroutine 共享变量读写没有可见性保证（代码实证见 §2.4.5）
- ⬜ **goroutine 泄漏**：无人接收的 channel、忘记 cancel 的 context；用 `runtime.NumGoroutine` 与 pprof goroutine profile 排查（代码实证见 §2.4.6）
- ⬜ **内存逃逸**：返回局部变量指针；`-gcflags=-m` 入门
- ⬜ **GC**：三色标记；STW 简化理解；GOGC

### 2.3 工程与标准库

- ⬜ **模块**：`go mod`；replace；版本选择 MVS
- ⬜ **testing**：表驱动；`t.Parallel`；benchmark `-bench`
- ⬜ **net/http**：Handler 接口；Server 与 Client
- ⬜ **net/http ServeMux 增强（Go 1.22+）**：模式里可写 HTTP 方法与路径参数 `GET /codes/{code}`；回答「为什么还用 Gin」的对比素材（代码实证见 §2.4.7）
- ⬜ **JSON**：tag `omitempty`；自定义 `MarshalJSON`
- ⬜ **泛型（Go 1.18+）**：用类型参数与约束让同一算法复用于多种类型；`any`、`comparable`、`~T` 与类型联合的写法见 [03 章 §1.5](./03-Go函数接口与错误处理.md)

#### 2.4.1 for 循环变量：Go 1.22 前后答案完全不同

**为什么重要**：「for range + goroutine 闭包捕获循环变量」是最经典的 Go 并发面试题，而 Go 1.22（2024-02 发布）改变了它的标准答案。按旧八股回答，面试官会认为你知识陈旧；只知道新行为、不知道旧陷阱，追问「老代码为什么要写 `i := i`」时又会卡住。两头都要会。

**文件**：`F:\study\code\interview-lab\forloop\main.go`

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println("i =", i)
		}()
	}
	wg.Wait()
}
```

**运行**（PowerShell，在 `F:\study\code\interview-lab` 下）：

```powershell
go run .\forloop\
```

**输出**（顺序随机，但一定是 0、1、2 各一次）：

```text
i = 2
i = 0
i = 1
```

**逐段讲解**：

- **Go 1.22 起**：`for` 的循环变量 `i` 在**每次迭代都是一个新变量**，三个 goroutine 各自捕获自己那份，所以输出 0、1、2。
- **Go 1.21 及以前**：整个循环只有**一个** `i`，三个 goroutine 共享它。goroutine 真正跑起来时循环往往已结束，`i` 已变成 3，典型输出是 `3 3 3`（也可能夹杂别的值，属于数据竞争）。旧代码的两种修法：循环体内 `i := i` 重新声明，或 `go func(i int){...}(i)` 传参。
- **关键细节（面试加分点）**：新旧语义由 **go.mod 里的 `go` 指令版本**决定，不是由编译器版本决定。用 Go 1.26 编译一个 `go.mod` 写着 `go 1.21` 的模块，仍然是旧语义——这是为了兼容老代码。你可以把本模块 go.mod 里的 `go` 那一行（内容取决于你安装的版本，如 `go 1.26.5`）手动改成 `go 1.21` 再跑一次，观察输出变成 3 3 3（体验完记得改回来）。

**顺带一个新写法**：Go 1.25+ 的 `sync.WaitGroup` 新增了 `Go` 方法，一步封装 `Add(1)` + `Done`，从根上避免「Add 忘写 / Done 不配对」：

**文件**：`F:\study\code\interview-lab\wggo\main.go`（需要 Go 1.25+）

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Go(func() { fmt.Println("i =", i) }) // 内部自动 Add(1)，f 结束自动 Done
	}
	wg.Wait()
}
```

```powershell
go run .\wggo\
```

**面试口径**：「Add 要写在 go 语句之前」的原则依然正确；Go 1.25+ 项目里优先用 `wg.Go(f)`。

#### 2.4.2 map 并发写：是 fatal error，不是普通 panic，recover 救不了

**为什么重要**：很多八股写「map 并发写会 panic」，这是**不精确的**，而且是面试官最爱的追问点：「那能不能用 recover 兜住？」——答「能」直接暴露没实践过。真相：并发写 map 触发的是 `fatal error: concurrent map writes`，由 `runtime.throw` 抛出，**不是 panic，recover 无效，进程直接崩溃**。

**文件**：`F:\study\code\interview-lab\panicdemo\main.go`

```go
package main

import "fmt"

func main() {
	// 实验 1：向已关闭 channel 发送 → 普通 panic，可以被 recover 救回来
	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Println("recover 捕获到了:", r)
			}
		}()
		ch := make(chan int)
		close(ch)
		ch <- 1 // panic: send on closed channel
	}()
	fmt.Println("程序还活着，说明这种 panic 可以 recover")

	// 实验 2：map 并发写 → fatal error，recover 也救不回来。
	// 把下面注释取消再运行，进程会直接崩溃退出，
	// 打印 fatal error: concurrent map writes——上面的 recover 套路完全无效。
	//
	// m := map[int]int{}
	// go func() {
	// 	for {
	// 		m[1] = 1
	// 	}
	// }()
	// for {
	// 	m[2] = 2
	// }
}
```

```powershell
go run .\panicdemo\
```

**输出**：

```text
recover 捕获到了: send on closed channel
程序还活着，说明这种 panic 可以 recover
```

然后把实验 2 的注释取消再跑一次，你会看到进程直接崩溃打印 `fatal error: concurrent map writes`，`recover` 完全帮不上忙。**对比记忆表**：

| 触发场景 | 类型 | 能否 recover |
|----------|------|--------------|
| 向已关闭 channel 发送 | panic | ✅ 能 |
| 数组/切片越界、空指针解引用 | panic | ✅ 能 |
| map 并发读写 / 并发写 | fatal error（runtime.throw） | ❌ 不能，进程必死 |
| 死锁 `all goroutines are asleep` | fatal error | ❌ 不能 |

**面试口径**：并发访问 map 的正确做法是 `sync.RWMutex` 保护普通 map，或特定场景用 `sync.Map`（见 §2.4.4）；开发期用 `go run -race` 提前暴露（`-race` 能在真正崩溃前报告数据竞争）。

#### 2.4.3 new vs make、方法集与值/指针接收者

**为什么重要**：这两个是 Go 八股出现频率最高的语言题之一，而且能用 10 行代码彻底搞懂。

**文件**：`F:\study\code\interview-lab\newmake\main.go`

```go
package main

import "fmt"

// Counter 是演示方法集用的小结构体
type Counter struct{ n int }

func (c *Counter) Inc()       { c.n++ }      // 指针接收者：会修改自身
func (c Counter) Value() int  { return c.n } // 值接收者：只读

// Incrementer 接口只要求一个 Inc 方法
type Incrementer interface{ Inc() }

func main() {
	// --- new vs make ---
	// new(T)：给任意类型 T 分配一块清零内存，返回指针 *T
	p := new([]int)        // p 的类型是 *[]int
	fmt.Println(*p == nil) // true：指向的是 nil 切片，还不能下标赋值

	// make：只用于 slice / map / channel 三种，返回“初始化好、能直接用”的 T 本身
	s := make([]int, 3)       // len=3，可直接 s[0]=1
	m := make(map[string]int) // 可直接写入；var m map[string]int 则写入会 panic
	m["a"] = 1
	s[0] = 1
	fmt.Println(s, m)

	// --- 方法集 ---
	// *Counter 的方法集 = {Inc, Value}；Counter 的方法集 = {Value}
	var i Incrementer = &Counter{} // OK：指针能满足接口
	// var j Incrementer = Counter{} // 编译错误：Inc 的接收者是 *Counter，值类型不满足
	i.Inc()
	fmt.Println("count =", i.(*Counter).Value())
}
```

```powershell
go run .\newmake\
```

**输出**：

```text
true
[1 0 0] map[a:1]
count = 1
```

**面试口径**（两句话版）：

1. `new(T)` 对任意类型分配零值内存、返回 `*T`；`make` 只服务 slice/map/chan 三种引用类型，做的是「分配 + 内部结构初始化」，返回 T 本身。日常几乎不用 `new`，struct 用 `&T{}` 更常见。
2. 方法集规则：`*T` 拥有全部方法（值接收者 + 指针接收者），`T` 只拥有值接收者方法——所以指针接收者方法会让「值类型」满足不了接口。经验法则：**同一类型的方法接收者保持一致，需要修改自身或结构体较大时统一用指针接收者**。把上面被注释的 `var j Incrementer = Counter{}` 取消注释，亲眼看一次编译错误。

#### 2.4.4 sync.Once / atomic / sync.Map：什么时候不用 Mutex

**为什么重要**：面试常问「除了 Mutex 还知道哪些并发工具，各自什么场景」。答案有三层：只需初始化一次用 `Once`；只是并发加减一个数用 `atomic`；读多写少且 key 基本固定的映射可用 `sync.Map`——**都不满足时才回到 Mutex**。

**文件**：`F:\study\code\interview-lab\syncextra\main.go`

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var wg sync.WaitGroup

	// 1) sync.Once：并发环境下某段代码只执行一次（懒加载单例、初始化配置）
	var once sync.Once
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			once.Do(func() { fmt.Println("这行只会打印一次") })
		}()
	}
	wg.Wait()

	// 2) atomic：单个数值的无锁并发安全操作，比 Mutex 更轻
	var n atomic.Int64
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			n.Add(1)
		}()
	}
	wg.Wait()
	fmt.Println("atomic 计数 =", n.Load()) // 恒为 1000；换成普通 int n++ 就会少

	// 3) sync.Map：为“读多写少 + key 基本固定”优化；一般场景仍推荐 map + RWMutex
	var sm sync.Map
	sm.Store("hit", 42)
	if v, ok := sm.Load("hit"); ok {
		fmt.Println("sync.Map 读到 =", v)
	}
}
```

```powershell
go run .\syncextra\
```

**输出**：

```text
这行只会打印一次
atomic 计数 = 1000
sync.Map 读到 = 42
```

**逐点讲解**：

- **sync.Once**：`once.Do(f)` 保证 f 在所有 goroutine 中总共只执行一次，且其他 goroutine 会**等它执行完**再继续（不是跳过就跑）。典型用途：数据库连接、全局配置的懒加载。Go 1.21+ 还有便捷封装 `sync.OnceValue(f)`，把「只算一次的结果」缓存起来。
- **atomic**：Go 1.19+ 推荐用类型化的 `atomic.Int64`/`atomic.Bool`/`atomic.Pointer[T]`，比旧的 `atomic.AddInt64(&x, 1)` 函数式写法不易用错。适用面很窄——**只保护单个数值/指针**；要保护「多个字段一起变」的复合状态，必须用锁。
- **sync.Map**：官方文档明确说它只为两类场景优化：① 每个 key 只写一次、读很多次（缓存）；② 不同 goroutine 操作不相交的 key 集合。其他场景 `map + sync.RWMutex` 更快也更好懂。面试说「map 不安全所以我都用 sync.Map」是**减分**答案。

#### 2.4.5 Go 内存模型与 happens-before：为什么不加同步的共享变量不可靠

**为什么重要**：面试官问「一个 goroutine 写变量、另一个读，不加锁会怎样」，期望你答出「没有 happens-before 关系就没有可见性保证」，而不是「大概率没问题」。**happens-before** 是内存模型术语：若操作 A happens-before 操作 B，则 B 保证能看到 A 的写入；没有这个关系，编译器和 CPU 都可能重排、缓存，读到旧值甚至永远读不到新值。

**文件**：`F:\study\code\interview-lab\happens\main.go`

```go
package main

import "fmt"

var msg string

func main() {
	done := make(chan struct{})
	go func() {
		msg = "hello"
		close(done) // 关闭 channel 的写入，happens-before 收到关闭信号的读取
	}()
	<-done
	fmt.Println(msg) // 保证读到 "hello"，因为 channel 建立了同步关系
}
```

```powershell
go run .\happens\
```

**输出**：`hello`（**保证**，不是碰巧）。

**讲解**：

- 这段代码正确的原因：Go 内存模型规定「对 channel 的发送/关闭 happens-before 对应的接收完成」。`msg = "hello"` 先于 `close(done)`，`close(done)` happens-before `<-done` 返回，所以主 goroutine 必然看到 `msg` 的新值。
- **反面教材**（片段，不要写进文件，仅供理解）：用普通 bool 变量忙等是错的——

  ```go
  // 片段：错误示范，没有任何同步原语
  var ready bool
  go func() { msg = "hello"; ready = true }()
  for !ready { } // 数据竞争！可能死循环，也可能读到空 msg
  ```

  没有 channel/锁/atomic 建立同步，`ready = true` 对主 goroutine **可能永远不可见**。如果把这段反面教材真写成程序、用 `go run -race` 跑，会立刻打印 `WARNING: DATA RACE`。养成习惯：并发代码一律先用 `-race` 跑一遍，它报告的每一条都是真 bug。
- **能建立 happens-before 的常用手段**：channel 收发、`mutex.Unlock → 下一次 Lock`、`WaitGroup.Done → Wait 返回`、`once.Do`、atomic 操作。面试一句话：「Go 的口号是 *Don't communicate by sharing memory; share memory by communicating*，内存模型层面就是靠这些原语建立 happens-before」。

#### 2.4.6 goroutine 泄漏：最常见的模式与排查

**为什么重要**：「goroutine 会泄漏吗？怎么排查？」是中级 Go 面试必问。goroutine 不会被 GC 主动杀掉——只要它还阻塞在某个 channel/锁上，栈和它引用的对象就一直占着内存。

**文件**：`F:\study\code\interview-lab\leak\main.go`

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// leak 演示最常见的 goroutine 泄漏：往无缓冲 channel 发送但没人接收
func leak() {
	ch := make(chan int) // 无缓冲
	go func() {
		ch <- 1 // 没有接收方，这个 goroutine 永远阻塞在这一行
	}()
	// 函数返回了，但上面那个 goroutine 永远回收不掉 —— 泄漏
}

func main() {
	fmt.Println("初始 goroutine 数:", runtime.NumGoroutine())
	for i := 0; i < 100; i++ {
		leak()
	}
	time.Sleep(100 * time.Millisecond) // 等 goroutine 都跑到阻塞点
	fmt.Println("泄漏后 goroutine 数:", runtime.NumGoroutine())
}
```

```powershell
go run .\leak\
```

**输出**：

```text
初始 goroutine 数: 1
泄漏后 goroutine 数: 101
```

**讲解**：

- 100 次调用留下 100 个永远阻塞在 `ch <- 1` 的 goroutine。真实项目里的同款场景：超时放弃等待结果，但干活的 goroutine 还在往 channel 里塞结果。
- **三种修法**：① 结果 channel 给缓冲 `make(chan int, 1)`，发送方塞完即走；② 发送方用 `select { case ch <- v: case <-ctx.Done(): return }`，取消时能退出；③ 谁启动 goroutine，谁负责给它退出路径（context 传进去并保证会 cancel）。
- **线上排查**：`runtime.NumGoroutine()` 做成 Prometheus 指标看趋势；确认泄漏后用 pprof 的 goroutine profile 看阻塞在哪一行（`go tool pprof http://localhost:6060/debug/pprof/goroutine`，服务里要先挂 `net/http/pprof`）。pprof 的完整用法在 [16 章](./16-Go运行时内存GC与性能分析.md)。

## 3. MySQL（14 项）

- ⬜ **InnoDB**：聚簇索引；主键选择对性能影响
- ⬜ **日志体系**：redo log（crash-safe）/ undo log（回滚 + MVCC）/ binlog（复制与恢复）；两阶段提交（详见 §3.1）
- ⬜ **buffer pool**：数据页的内存缓存；脏页与刷盘；为何「改一行」不等于「立刻写磁盘」（详见 §3.1）
- ⬜ **B+ 树**：为何 MySQL 用 B+ 而非 B 树
- ⬜ **最左前缀**：联合索引 `(a,b,c)` 只有条件从最左列连续覆盖才能高效定位；`where b=1 and c=2` 得不到期望的范围查找收益（优化器仍可能选择扫这棵索引树）。补充：MySQL 8.0.13+ 在首列 `a` 基数很低时可能走 Index Skip Scan（对每个 a 值分别做 b,c 的范围定位），但一般数据分布下仍应把等值条件放最左列，以 `EXPLAIN` 实测为准
- ⬜ **覆盖索引**：Using index；减少回表
- ⬜ **EXPLAIN**：type、key、rows、Extra 各代表什么
- ⬜ **事务 ACID**：InnoDB 如何保证
- ⬜ **隔离级别**：脏读/不可重复读/幻读；MVCC 一句话
- ⬜ **间隙锁 / 临键锁**：RR 下防幻读
- ⬜ **索引失效**：函数、隐式转换、 `%like`、or 不当
- ⬜ **慢 SQL 排查**：慢日志、EXPLAIN、索引优化；手写 SQL 面试题也多围绕索引设计、慢查询与深分页（deep paging）优化方案出题
- ⬜ **分库分表**：垂直/水平；全局 ID（雪花）
- ⬜ **短链表设计**：`short_code` 唯一索引；长 URL 长度；分片键（见 [08 设计](../系统设计/08-短链服务设计.md)）

**RR、MVCC 与间隙锁的精确口径（高频追问）**：RR 下解决「不可重复读」的是 MVCC 快照读——整个事务复用同一个一致性视图（Read View），两次读走同一份快照，结果自然一致。防「幻读」的是当前读（`select ... for update` 等）用的临键锁 = 记录锁 + 间隙锁：**记录锁防已有行被改，间隙锁锁的是索引记录之间的间隙、防区间内插入新行**。别把间隙锁和不可重复读直接挂钩——面试官追问「间隙锁锁的是什么」，要答「索引记录之间的间隙，防插入」。

### 3.1 MySQL 日志体系与 buffer pool（面试最高频，先懂流程再背名词）

**为什么重要**：「一条 UPDATE 语句在 InnoDB 里发生了什么」几乎是 MySQL 面试的第一梯队问题，考的就是 buffer pool + 三种日志的配合——把下面这个流程讲顺，§3 里 ACID、MVCC、主从复制好几个条目就同时串起来了。

**先建立画面：一条 `UPDATE user SET name='b' WHERE id=1` 的完整旅程**

```text
客户端 → Server 层(解析/优化) → InnoDB 引擎
                                   │
  1. 目标数据页在 buffer pool 吗？ 不在则从磁盘读入内存
  2. 写 undo log        —— 记录旧值 name='a'（用于回滚 + MVCC 旧版本读）
  3. 改 buffer pool 中的页 —— 内存里 name 变成 'b'，该页成为「脏页」
  4. 写 redo log (prepare) —— 顺序追加“页 X 偏移 Y 改成 Z”，物理日志
  5. 写 binlog           —— Server 层逻辑日志，记录“这条 SQL/行变更”
  6. redo log 置为 commit —— 两阶段提交完成，事务成功
  （脏页由后台线程稍后刷回磁盘，跟事务提交不同步）
```

**三种日志各管什么（口述模板）**：

| 日志 | 归属 | 记什么 | 解决什么问题 |
|------|------|--------|--------------|
| redo log | InnoDB 引擎层 | 物理改动（哪页哪偏移改成什么），循环写 | **crash-safe**：宕机后重放 redo，把「已提交但脏页没落盘」的数据找回来。本质是 WAL（Write-Ahead Logging，先顺序写日志再慢慢刷数据页），顺序写远快于随机写，这是「改内存也敢说提交成功」的底气 |
| undo log | InnoDB 引擎层 | 逻辑旧值（反向操作） | **回滚**（事务失败恢复原值）+ **MVCC**（快照读沿版本链找旧版本，见隔离级别条目） |
| binlog | Server 层（所有引擎共有） | 逻辑变更（语句或行格式） | **主从复制**（从库重放）+ **备份/按时间点恢复** |

**两阶段提交为什么必须有**：redo log 和 binlog 是两份独立日志，必须要么都写成功、要么都作废，否则崩溃恢复后主库（靠 redo）和从库（靠 binlog）数据会不一致。流程：redo 先写成 prepare 态 → 写 binlog → redo 改成 commit 态。恢复时规则：redo 是 commit 的直接生效；redo 是 prepare 的看对应 binlog 是否完整，完整则提交、不完整则回滚。**一句话答法**：「两阶段提交把 binlog 当作事务是否成立的仲裁者，保证 redo 与 binlog 逻辑一致」。

**buffer pool 口述版**：InnoDB 以「页」（默认 16KB）为单位管理数据，buffer pool 就是页的内存缓存（改良版 LRU，分冷热区防全表扫描把热点页冲掉）。读：先查 buffer pool，未命中才读盘。写：只改内存页并标记为脏页，后台异步刷盘。所以 MySQL 的写性能来自「内存改页 + 顺序写 redo」，而不是每次改动都随机写磁盘。

**可跟做验证**（需要 [13 章](./13-Docker与Linux部署Go服务.md) 的 MySQL 容器已启动；片段，在 MySQL 客户端里执行）：

```powershell

docker exec -it mysql8 mysql -uroot -p
```

```sql

SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'; -- 1=每次提交刷 redo 到磁盘（最安全）
```

- ⬜ **哨兵 / Cluster**：高可用与槽位；Cluster 知道槽位分配与 `MOVED` 重定向即可，面试中单主 + 哨兵问得更高频
- ⬜ **缓存穿透**：查不存在的 key，每次都打穿到 DB——布隆过滤器；空值缓存（08 短链）
- ⬜ **缓存击穿**：热点 key 过期瞬间请求直打 DB——互斥锁；逻辑过期
- ⬜ **缓存雪崩**：TTL 随机；多级缓存
- ⬜ **Cache Aside**：先更 DB 再删缓存；延迟双删
- ⬜ **分布式锁**：SET NX EX；Lua 解锁；Redlock 争议
- ⬜ **短链缓存**：`code→URL`；302 前查 Redis（[11 章](./11-短链服务项目实战下.md)）

### 4.1 大 key / 热 key 与 pipeline（追问率上升的三件套）

**为什么重要**：缓存三兄弟（穿透/击穿/雪崩）已经人均会背，面试官开始转问更贴近生产的：「Redis 单线程，一个大 key 会怎样？」「热 key 打满一个分片怎么办？」「怎么减少网络往返？」

**大 key**：单个 key 的 value 过大（如几 MB 的 String、几十万成员的 ZSet）。危害：Redis 是单线程执行命令，读写大 key 会**阻塞后面所有请求**；网络传输放大；`DEL` 大集合本身就是慢操作。治理：**拆**（一个大 Hash 按 field 哈希拆成多个小 key）、**删用 `UNLINK`**（后台线程异步释放内存，不阻塞主线程）、写入侧控制集合大小上限。

**热 key**：单个 key 的访问 QPS 极高（如爆款短码）。危害：Cluster 下这个 key 只落在一个分片，单分片被打满，加节点也没用。治理：**本地缓存**（进程内 map + 短 TTL，挡掉绝大多数读）、**key 加随机后缀拆成多副本**（`hot:1`～`hot:N` 随机读一个，写时全写）、只读流量走从节点。短链项目答法：热点短码用「本地缓存 30s + Redis + singleflight 防击穿」三层。

**识别命令**（片段，「服务器上」或容器里执行；PowerShell 下先 `docker exec -it redis-lab sh` 进容器，`redis-lab` 容器的创建命令见本节下文「准备」）：

```bash
# 片段：容器/服务器 shell 内执行
redis-cli --bigkeys                 # 抽样扫描各类型的最大 key
redis-cli MEMORY USAGE some_key     # 精确查看单个 key 占用字节数
redis-cli --hotkeys                 # 找热 key（要求 maxmemory-policy 为 allkeys-lfu）
```

**pipeline**：默认每条命令都要一次「请求→响应」网络往返（RTT），100 条命令 = 100 个 RTT；pipeline 把 N 条命令一次性发出、一次性收回，往返成本从 N 降到 1。下面用 go-redis 实测对比。

**准备**（PowerShell，仍在 `F:\study\code\interview-lab` 模块下；需要 Docker Desktop，见 [13 章](./13-Docker与Linux部署Go服务.md)）：

```powershell

go get github.com/redis/go-redis/v9    # 本教程验证于 v9.21.0，v9 均可
```

**文件**：`F:\study\code\interview-lab\pipeline\main.go`

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()
	if err := rdb.Ping(ctx).Err(); err != nil {
		fmt.Println("连不上 Redis，请先启动:", err)
		return
	}

	// 写法 1：逐条发送，100 条命令 = 100 次网络往返
	start := time.Now()
	for i := 0; i < 100; i++ {
		if err := rdb.Set(ctx, fmt.Sprintf("k:%d", i), i, time.Minute).Err(); err != nil {
			fmt.Println("SET 失败:", err)
			return
		}
	}
	fmt.Println("逐条发送耗时:", time.Since(start))

	// 写法 2：pipeline 打包，100 条命令 ≈ 1 次网络往返
	start = time.Now()
	pipe := rdb.Pipeline()
	for i := 0; i < 100; i++ {
		pipe.Set(ctx, fmt.Sprintf("p:%d", i), i, time.Minute)
	}
	if _, err := pipe.Exec(ctx); err != nil {
		fmt.Println("pipeline 执行失败:", err)
		return
	}
	fmt.Println("pipeline 耗时:", time.Since(start))
}
```

```powershell
go run .\pipeline\
```

本机 Docker 环回网络 RTT 极小，也能看到 pipeline 快一个数量级；真实机房 RTT 零点几毫秒起步，差距更大。

**必须分清的边界（面试追问点）**：pipeline **只省往返，不保证原子**——打包的命令之间可能插入其他客户端的命令，某条失败其余照常执行。需要原子性用 `MULTI/EXEC` 事务（go-redis 里 `TxPipeline`）或 Lua 脚本（单脚本执行期间不会被打断，分布式锁解锁就靠它，见 §4 分布式锁条目）。

### 5.1 拥塞控制与 HTTP/3（口述版）

**先分清两个「控制」**——这是最容易混的追问点：

- **流量控制**：别把**接收方**撑死。接收方在 ACK 里通告自己还能收多少（接收窗口 rwnd），发送方不超发。
- **拥塞控制**：别把**网络**撑死。发送方自己维护一个拥塞窗口 cwnd，根据丢包/延迟探测网络容量。实际发送量 = min(rwnd, cwnd)。

**拥塞控制四阶段（经典 Reno 口述版）**：

```text
cwnd
 │           丢包(超时)→ cwnd 重回起点
 │      ／│         ／
 │    ／  │       ／   ← 拥塞避免：每 RTT 线性 +1
 │  ／    │     ／
 │ /      │   /  ← 3 个重复 ACK → 快重传+快恢复：
 │/       │  /      cwnd 减半后继续线性涨（不用回到 1）
 └────────┴──────────────────────→ 时间
  ↑慢启动：每 RTT 翻倍（指数），涨到阈值 ssthresh 转线性
```

1. **慢启动**：连接刚建立时不知道网络多宽，cwnd 从很小开始，每个 RTT **翻倍**（指数增长）——名字叫慢，涨得其实快，「慢」指起点低。
2. **拥塞避免**：cwnd 达到阈值 ssthresh 后改为每个 RTT **加 1**（线性），小心试探上限。
3. **快重传**：收到 **3 个重复 ACK**（说明中间丢了个包但后面的还在到），不等超时立刻重传丢的那个。
4. **快恢复**：快重传后认为网络只是轻度拥塞，ssthresh 与 cwnd 减半后继续线性涨；而**超时丢包**被视为重度拥塞，cwnd 直接打回起点重新慢启动。

加分点：现代 Linux 默认算法是 CUBIC（窗口按三次曲线恢复）；Google 的 BBR 不依赖丢包信号，靠测带宽和 RTT，适合高丢包长肥管道。说出名字即可，不用展开。

**可跟做观察**（PowerShell，本机即可）：

```powershell
netstat -s -p tcp   # 看 "Segments Retransmitted"（中文界面显示为 "重新传输的段"）计数——非零就是发生过重传
```

服务器上（Linux）可用 `ss -ti` 看到每条连接的 `cwnd`、`ssthresh`、重传数；Windows 上没有直接等价物，面试说 Linux 命令即可。

**HTTP 队头阻塞的三层递进（把 1.1 → 2 → 3 串成一条线，面试最出彩的讲法）**：

1. **HTTP/1.1**：一条连接上请求必须排队（管线化名存实亡），前一个响应没回来后面全等——**应用层队头阻塞**。浏览器只好开 6 条并发连接硬扛。
2. **HTTP/2**：一条 TCP 连接里多路复用无数流，应用层队头阻塞解决了。**但 TCP 层还有**：TCP 保证字节流有序，只要丢一个包，这条连接上**所有流**都得停下来等重传——TCP 根本不知道「流」的存在。
3. **HTTP/3**：换掉 TCP，用 **QUIC（跑在 UDP 上，把可靠传输、加密握手做进用户态协议）**。每个流独立做丢包恢复，丢包只卡自己那个流——TCP 层队头阻塞被彻底解决。附赠：**0-RTT/1-RTT 握手**（QUIC 把传输握手与 TLS 1.3 握手合并，比 TCP+TLS 的多轮往返快）、**连接迁移**（连接由 Connection ID 标识而非四元组，手机从 Wi-Fi 切到流量不断连）。

**可跟做观察**：打开浏览器 DevTools → Network → 右键表头勾选 Protocol 列，访问大站（如 google.com、cloudflare.com），看到 `h3` 就是 HTTP/3，`h2` 是 HTTP/2。（`curl.exe` 需要特殊构建才支持 `--http3`，用浏览器看最省事。）

### 7.1 Raft 与 etcd：从一句话到三分钟

**为什么重要**：上面「服务发现」条目提到 Consul、K8s——面试官顺势就会问「它们底下怎么保证多个节点数据一致？」答案是共识算法 Raft。入门岗不要求推导，但要能讲清三要素。

**一句话版**：Raft 让一组节点先选出一个 leader，所有写都走 leader，leader 把日志复制到**多数派**（超过半数）节点后才算提交——少数节点挂了不影响正确性。

**三分钟版（三要素）**：

1. **Leader 选举**：节点有三种角色 leader / follower / candidate。follower 一段时间（选举超时，**随机化**以避免同时发起选举瓜分选票）没收到 leader 心跳，就自增任期号 term、变成 candidate 拉票；拿到多数派选票即成为新 leader。term 是逻辑时钟，旧 leader 网络恢复后发现自己 term 落后会自动退位——这就防了「双主」（脑裂）。
2. **日志复制**：客户端写请求到 leader，leader 先追加到本地日志，并行发给所有 follower；**多数派确认后才提交**并应用到状态机，然后应答客户端。挂掉一两个 follower 不影响写入（5 节点容忍 2 个挂）。
3. **安全性**：候选人日志不够新（term 更小或同 term 但更短）会被拒票，保证新 leader 一定包含所有已提交日志——不会「新官上任丢旧账」。

**和 CAP 挂钩（面试串联点）**：Raft 系统是典型 **CP**——网络分区时，少数派那边选不出 leader、拒绝写入，牺牲可用性换一致性。etcd（K8s 的元数据存储，Go 写的）和 Consul 都用 Raft。

**可选小实验**（PowerShell + Docker，5 分钟体验 etcd；不做不影响面试）：

```powershell
docker run -d --name etcd-lab -p 2379:2379 -e ALLOW_NONE_AUTHENTICATION=yes -e ETCD_ADVERTISE_CLIENT_URLS=http://localhost:2379 bitnami/etcd:latest
docker exec etcd-lab etcdctl put hello world
docker exec etcd-lab etcdctl get hello
# 输出:
# hello
# world
docker rm -f etcd-lab   # 玩完删掉
```

单节点没有「多数派」可言，仅体验 API；真集群至少 3 节点。**面试口径**：「我理解 Raft 的选举、日志复制和多数派提交，本地用 etcd 单节点玩过 put/get；生产级调优没做过，不多讲。」——诚实边界比吹会更加分（呼应 §8.2）。

### 12.1 六类题型 Go 参考模板（完整可编译）

有 C++ 竞赛底子的话，这些题的算法本身你都会——要练的是 **Go 的表达方式**：没有 STL，`map` 代替 `unordered_map`，`container/list` 代替 `std::list`，切片当队列，并发题用 channel。六个模板放在一个文件里，跑一次全部验证。

**文件**：`F:\study\code\interview-lab\algos\main.go`（沿用 §2.4 建好的模块）

```go
// 六类高频手撕题的 Go 参考模板，全部可编译运行。
package main

import (
	"container/list"
	"fmt"
	"sync"
)

// ---------- 1. 两数之和：map 存补数 ----------

func twoSum(nums []int, target int) []int {
	seen := make(map[int]int, len(nums)) // 值 -> 下标
	for i, v := range nums {
		if j, ok := seen[target-v]; ok {
			return []int{j, i}
		}
		seen[v] = i
	}
	return nil
}

// ---------- 2. LRU：map + 双向链表 ----------

type entry struct{ key, value int }

type LRUCache struct {
	cap   int
	ll    *list.List            // 队首 = 最近使用，队尾 = 最久未用
	items map[int]*list.Element // key -> 链表节点，O(1) 定位
}

func NewLRU(capacity int) *LRUCache {
	return &LRUCache{
		cap:   capacity,
		ll:    list.New(),
		items: make(map[int]*list.Element, capacity),
	}
}

func (c *LRUCache) Get(key int) (int, bool) {
	el, ok := c.items[key]
	if !ok {
		return 0, false
	}
	c.ll.MoveToFront(el) // 访问过 = 最近使用，挪到队首
	return el.Value.(*entry).value, true
}

func (c *LRUCache) Put(key, value int) {
	if el, ok := c.items[key]; ok { // 已存在：改值 + 挪队首
		el.Value.(*entry).value = value
		c.ll.MoveToFront(el)
		return
	}
	if c.ll.Len() >= c.cap { // 满了：淘汰队尾（最久未用）
		back := c.ll.Back()
		c.ll.Remove(back)
		delete(c.items, back.Value.(*entry).key)
	}
	c.items[key] = c.ll.PushFront(&entry{key, value})
}

// ---------- 3. 反转链表：三指针 ----------

type ListNode struct {
	Val  int
	Next *ListNode
}

func reverseList(head *ListNode) *ListNode {
	var prev *ListNode // 初始为 nil，最终成为新表头前的“地板”
	cur := head
	for cur != nil {
		next := cur.Next // 先存住后继，否则改了 Next 就找不到了
		cur.Next = prev  // 指针反向
		prev, cur = cur, next
	}
	return prev
}

// ---------- 4. 二叉树层序遍历：BFS 队列 ----------

type TreeNode struct {
	Val         int
	Left, Right *TreeNode
}

func levelOrder(root *TreeNode) [][]int {
	if root == nil {
		return nil
	}
	var res [][]int
	queue := []*TreeNode{root}
	for len(queue) > 0 {
		var level []int
		var next []*TreeNode
		for _, node := range queue {
			level = append(level, node.Val)
			if node.Left != nil {
				next = append(next, node.Left)
			}
			if node.Right != nil {
				next = append(next, node.Right)
			}
		}
		res = append(res, level)
		queue = next
	}
	return res
}

// ---------- 5. 快排 + 二分 ----------

func quickSort(nums []int, lo, hi int) {
	if lo >= hi {
		return
	}
	pivot := nums[hi] // 取最后一个当基准（面试可提：随机化避免最坏 O(n²)）
	i := lo
	for j := lo; j < hi; j++ {
		if nums[j] < pivot {
			nums[i], nums[j] = nums[j], nums[i]
			i++
		}
	}
	nums[i], nums[hi] = nums[hi], nums[i]
	quickSort(nums, lo, i-1)
	quickSort(nums, i+1, hi)
}

func binarySearch(nums []int, target int) int {
	lo, hi := 0, len(nums)-1
	for lo <= hi {
		mid := lo + (hi-lo)/2 // 防溢出写法，比 (lo+hi)/2 稳
		switch {
		case nums[mid] == target:
			return mid
		case nums[mid] < target:
			lo = mid + 1
		default:
			hi = mid - 1
		}
	}
	return -1
}

// ---------- 6. 两个 goroutine 交替打印奇偶：channel 当令牌 ----------

func printOddEven(n int) {
	oddTurn := make(chan struct{}, 1) // 缓冲 1：最后一次“交棒”没人接也不阻塞
	evenTurn := make(chan struct{}, 1)
	var wg sync.WaitGroup
	wg.Add(2)
	go func() { // 奇数打印者
		defer wg.Done()
		for i := 1; i <= n; i += 2 {
			<-oddTurn // 等到自己的令牌
			fmt.Print(i, " ")
			evenTurn <- struct{}{} // 交棒给偶数方
		}
	}()
	go func() { // 偶数打印者
		defer wg.Done()
		for i := 2; i <= n; i += 2 {
			<-evenTurn
			fmt.Print(i, " ")
			oddTurn <- struct{}{}
		}
	}()
	oddTurn <- struct{}{} // 发令：奇数先跑
	wg.Wait()
	fmt.Println()
}

// ---------- 演示入口 ----------

func main() {
	fmt.Println("1. twoSum:", twoSum([]int{2, 7, 11, 15}, 9)) // [0 1]

	lru := NewLRU(2)
	lru.Put(1, 100)
	lru.Put(2, 200)
	lru.Get(1)      // 访问 1，此刻 2 变成最久未用
	lru.Put(3, 300) // 容量满，淘汰 2
	_, ok := lru.Get(2)
	fmt.Println("2. LRU: key 2 还在吗?", ok) // false

	l := &ListNode{1, &ListNode{2, &ListNode{3, nil}}}
	r := reverseList(l)
	fmt.Print("3. 反转链表: ")
	for p := r; p != nil; p = p.Next {
		fmt.Print(p.Val, " ")
	}
	fmt.Println() // 3 2 1

	root := &TreeNode{Val: 1,
		Left:  &TreeNode{Val: 2},
		Right: &TreeNode{Val: 3, Left: &TreeNode{Val: 4}}}
	fmt.Println("4. 层序遍历:", levelOrder(root)) // [[1] [2 3] [4]]

	arr := []int{5, 2, 9, 1, 7}
	quickSort(arr, 0, len(arr)-1)
	fmt.Println("5. 快排:", arr, "二分找 7 的下标:", binarySearch(arr, 7))

	fmt.Print("6. 交替打印 1~10: ")
	printOddEven(10)
}
```

**逐题要点（面试怎么讲）**：

1. **两数之和**：一遍扫描，「先查补数、再存自己」——这个顺序天然处理了 `target = 2v` 时不会错用同一个元素。O(n) 时间 O(n) 空间。
2. **LRU**：不变式是「链表按最近使用排序，map 提供 O(1) 定位」。`Get`/`Put` 都是 O(1)。`el.Value.(*entry)` 是类型断言，因为 `container/list` 存的是 `any`（§2 的 type assertion 条目在这里落地）。加分句：「生产上 Redis 的近似 LRU 是抽样淘汰，不维护完整链表，省内存」。
3. **反转链表**：`next` 必须先存——这是唯一容易写错的点。Go 的多重赋值 `prev, cur = cur, next` 一行完成推进。
4. **层序遍历**：Go 没有内置队列，用切片：本层 `queue`，下一层收集到 `next`，天然按层分组。
5. **快排**：Lomuto 分区（单指针从左扫，小于基准就换到前面）。二分的 `lo + (hi-lo)/2` 防溢出写法在 Go 里 int 是 64 位、几乎不会真溢出，但面试写出来是习惯分。
6. **奇偶交替**：channel 当令牌，「拿到令牌才打印，打完交棒」。缓冲设 1 的原因：最后一次交棒时对方 goroutine 可能已退出循环，无缓冲会永远阻塞造成 goroutine 泄漏（正是 §2.4.6 讲的模式）；缓冲 1 让最后一棒「放下就走」。

### 13.1 高频行为题与回答骨架

| 高频问题 | 回答骨架（用你自己的真事填充） |
|----------|------------------------------|
| 自我介绍（60～90 秒） | 背景一句（学校/专业 + 算法竞赛经历）→ 为什么转 Go 后端一句 → 短链项目一句（技术栈 + 一个可证明的亮点）→ 期待一句（想做什么方向）。竞赛经历别只说获奖，转译成工程语言：「对复杂度和数据结构敏感，定位性能问题快」 |
| 遇到过最大的困难/印象最深的 bug | 选一个**真实调试过程**：如 goroutine 泄漏、缓存与 DB 不一致、压测 P99 突刺。讲清「怎么发现（现象/指标）→ 怎么定位（pprof/日志/复现）→ 怎么修 → 学到什么」。有排查过程的 bug 比「项目做得很顺」加分得多 |
| 和别人意见不合怎么办 | 骨架：先弄清对方依据 → 用数据/实验说话（比如两种方案各写个 benchmark）→ 接受更优解，谁对听谁的。避免「我据理力争说服了他」这种独角戏答案 |
| 为什么选择我们公司 | 提前 10 分钟做功课：公司产品/技术博客/开源项目里挑 1～2 个具体的点。忌空话「贵司平台大」 |
| 你的缺点 | 说真实但在改进的：如「后端工程经验短，我的补法是每个组件都亲手部署压测过（13/14 章）」。忌「我太追求完美」 |

**校招/实习特别注意**：被问「项目是不是自己写的 / 用没用 AI」时，用 §8.2 的口径诚实回答——AI 辅助了什么、哪些是自己完成并能现场修改的。行为面撒谎被追问穿的代价远大于承认用了 AI。

### 13.2 反问环节：问什么、别问什么

面试官说「你有什么想问我的」——说「没有」等于放弃一次展示 + 一次收集信息的机会。**建议问**（挑 2～3 个）：

1. 团队目前的技术栈和 Go 版本？服务是单体还是微服务？（判断技术环境新旧）
2. 代码怎么保证质量——有 code review 和 CI 吗？测试要求什么程度？（判断工程文化，呼应 12 章）
3. 新人前三个月一般做什么？有 mentor 制度吗？（判断成长环境）
4. 团队现在最大的技术挑战是什么？（给面试官发挥空间，常能听到真话）
5. 业务方向和团队规模、上线频率？（判断业务健康度）

**别问**：只问薪资加班（留给 HR 环节或 offer 后谈）；「你们公司是做什么的」（暴露没做功课）；面试官刚讲过的内容再问一遍。
