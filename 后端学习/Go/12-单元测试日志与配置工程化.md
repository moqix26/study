## 1. 为什么需要工程化闭环

| 痛点 | 无工程化 | 有工程化 |
|------|----------|----------|
| 改 Base62 算法 | 手工点 Postman | `go test` 秒级反馈 |
| 线上 502 | 只有「挂了」 | JSON 日志带 `code`、`latency` |
| 测试/生产配置混 | 误连生产 Redis | `APP_ENV=prod` 自动切文件 |
| 多人手工改表 | 环境表结构不一致 | migration 有版本、有记录、有审核 |
| 只看“服务没挂” | 慢请求和缓存雪崩发现太晚 | RED + 业务指标提前告警 |
| PR 看起来没问题 | 竞态或升级脚本上线才爆 | CI 自动跑 race、迁移、E2E |
| `kill -9` 部署 | 跳转中断、统计丢失 | 优雅停机排空连接 |

**术语（Observability 可观测性）**：通过日志、指标、链路追踪理解系统运行状态。
**生活类比**：餐厅后厨有出菜计时器、温度探针、订单流水号——不是等顾客投诉才知道糊了。
**本章用到的地方**：§4 错误与日志、§5 migration、§6 shutdown、§7 指标与质量门禁。

## 2. `testing` 标准库

### 2.1 第一个可直接运行的表驱动测试

先在 PowerShell 建一个独立练习项目：

```powershell
New-Item -ItemType Directory -Force .\chapter12-demo | Out-Null
Set-Location .\chapter12-demo
go mod init example.com/chapter12
```

新建 `base62.go`（**完整可编译清单**）：

```go
package shorturl

const alphabet = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

func Base62Encode(n uint64) string {
	if n == 0 {
		return "0"
	}
	buf := make([]byte, 0, 11)
	for n > 0 {
		buf = append(buf, alphabet[n%62])
		n /= 62
	}
	for left, right := 0, len(buf)-1; left < right; left, right = left+1, right-1 {
		buf[left], buf[right] = buf[right], buf[left]
	}
	return string(buf)
}
```

新建 `base62_test.go`（**完整测试入口**）：

```go
package shorturl

import "testing"

func TestBase62Encode(t *testing.T) {
	tests := []struct {
		name  string
		input uint64
		want  string
	}{
		{name: "zero", input: 0, want: "0"},
		{name: "one", input: 1, want: "1"},
		{name: "base", input: 62, want: "10"},
		{name: "two digits max", input: 3843, want: "ZZ"},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Base62Encode(tt.input); got != tt.want {
				t.Errorf("Base62Encode(%d) = %q, want %q", tt.input, got, tt.want)
			}
		})
	}
}
```

运行：

```powershell
go test -v -cover .\...
go test -run TestBase62Encode .
go test -race .\...
```

> Go 1.22+ 的 `for range` 每轮都有新的循环变量，因此不再需要旧教程里的 `tt := tt`。本章基线是 Go 1.22+。`-race` 在 Windows 需要支持的 C 工具链；若本机提示 `-race requires cgo`，可在 CI/Linux 再执行，但不要因此删除门禁。

| 代码 | 含义 | 改错会怎样 |
|------|------|------------|
| `[]struct{...}` | 用例表 | 漏掉边界值时保护不足 |
| `t.Run` | 每行成为有名字的子测试 | 失败时不易定位 |
| `Errorf` | 记录失败后继续下一例 | 换成 `Fatalf` 会终止当前子测试 |

这种写法相比为每个输入单独写一个 Test 函数的优势：断言逻辑只写一份，新增边界用例只需在表里加一行数据，且失败输出会带上子测试名，直接指明是哪个用例挂了。

### 2.2 高频测试辅助 API

下面四个 API 都由测试运行器管理资源，比手写清理更可靠：

```go
// 片段：放进任意 xxx_test.go；base62 完整版见 §2.1。
func TestHelpers(t *testing.T) {
	t.Helper() // 通常应写在自定义断言/helper 函数里，使失败行指向调用者

	dir := t.TempDir() // 测试结束自动删除
	t.Setenv("APP_ENV", "test") // 测试结束自动恢复环境变量
	f, err := os.CreateTemp(dir, "config-*.yaml")
	if err != nil { t.Fatal(err) }
	t.Cleanup(func() { _ = f.Close() }) // 后进先出执行

for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {

```

### 2.3 测试替身：手写 fake 完整落地

**为什么先抽接口**：Service 只关心“按短码查 URL”，不应关心 MySQL 驱动。测试注入内存 fake，运行快且不误连生产库。新建 `service.go`（**完整可编译清单**）：

```go
package shorturl

import (
	"context"
	"errors"
)

var ErrURLNotFound = errors.New("short URL not found")

type URLRepository interface {
	Save(context.Context, string, string) error
	FindByCode(context.Context, string) (string, error)
}

type Service struct{ repo URLRepository }

func NewService(repo URLRepository) *Service { return &Service{repo: repo} }

func (s *Service) Create(ctx context.Context, code, target string) error {
	return s.repo.Save(ctx, code, target)
}
func (s *Service) Resolve(ctx context.Context, code string) (string, error) {
	return s.repo.FindByCode(ctx, code)
}
```

新建 `service_test.go`（**完整测试入口，fake 与测试都在此文件**）：

```go
package shorturl

import (
	"context"
	"testing"
)

type fakeRepo struct{ urls map[string]string }
func newFakeRepo() *fakeRepo { return &fakeRepo{urls: make(map[string]string)} }
func (f *fakeRepo) Save(_ context.Context, code, target string) error {
	f.urls[code] = target
	return nil
}
func (f *fakeRepo) FindByCode(_ context.Context, code string) (string, error) {
	target, ok := f.urls[code]
	if !ok { return "", ErrURLNotFound }
	return target, nil
}

func TestServiceResolve(t *testing.T) {
	repo := newFakeRepo()
	svc := NewService(repo)
	ctx := context.Background()
	if err := svc.Create(ctx, "go", "https://go.dev"); err != nil { t.Fatal(err) }
	got, err := svc.Resolve(ctx, "go")
	if err != nil { t.Fatal(err) }
	if got != "https://go.dev" { t.Fatalf("got %q", got) }
}
```

执行 `go test -v .\...`。手写 fake 最透明，适合小接口和面试；接口很多、调用顺序复杂时可选 `gomock`；想生成可读 mock 文件可选 `mockery`。不要因为工具方便而模拟内部实现，优先断言可观察行为。

package shorturl

import (
	"encoding/json"
	"net/http"
	"net/http/httptest"
	"testing"

	"github.com/gin-gonic/gin"

func TestHealthHandler(t *testing.T) {
	gin.SetMode(gin.TestMode)
	r := gin.New()
	r.GET("/healthz", func(c *gin.Context) { c.JSON(http.StatusOK, gin.H{"status": "ok"}) })

### 2.5 原生 Fuzz：自动寻找 Base62 边界

Fuzz（模糊测试）会不断生成输入，擅长找 panic 和边界错误。往返性质应为 `Decode(Encode(n)) == n`。先把逆运算补进 §2.1 的 `base62.go`（该文件 import 需加入 `"fmt"` 与 `"strings"`）：

```go
// 片段：追加到 §2.1 的 base62.go
func Base62Decode(s string) (uint64, error) {
	if s == "" {
		return 0, fmt.Errorf("base62: empty input")
	}
	var n uint64
	for i := 0; i < len(s); i++ {
		idx := strings.IndexByte(alphabet, s[i])
		if idx < 0 {
			return 0, fmt.Errorf("base62: invalid character %q at index %d", s[i], i)
		}
		// 演示版不做溢出检查：往返 fuzz 的输入都是 Encode 的合法输出（最长 11 位），不会溢出；
		// 若要接收任意外部字符串，需在此校验 n 是否将超过 math.MaxUint64/62。
		n = n*62 + uint64(idx)
	}
	return n, nil
}
```

然后在 `base62_test.go` 加：

```go
// 片段：属于 base62_test.go；Encode 完整版见 §2.1。
func FuzzBase62RoundTrip(f *testing.F) {
	for _, seed := range []uint64{0, 1, 61, 62, 3843} { f.Add(seed) }
	f.Fuzz(func(t *testing.T, n uint64) {
		encoded := Base62Encode(n)
		decoded, err := Base62Decode(encoded)
		if err != nil { t.Fatal(err) }
		if decoded != n { t.Fatalf("got %d, want %d", decoded, n) }
	})
}
```

运行 `go test -fuzz=FuzzBase62RoundTrip -fuzztime=10s .`。失败输入会写入 `testdata/fuzz`，应作为回归用例保留。

## 4. 错误契约与 zap 结构化日志

生产项目不能让 Repository、Service、Handler 各自随意返回字符串。推荐把错误分成三层：

```text
基础设施错误（MySQL/Redis/MQ）
        ↓ 使用 fmt.Errorf("find url: %w", err) 保留 cause
领域错误（ErrURLNotFound / ErrURLExpired / ErrURLDisabled）
        ↓ Handler 统一映射
HTTP 状态 + 稳定业务错误码 + 对用户安全的 message
```

### 4.1 领域错误与包装

§2.3 的 demo 里我们已经用过 `ErrURLNotFound`；下面放到 11 章短链项目的语境中，把三层契约真正走通。**关键是三层图中的「↓」发生在哪**：基础设施错误必须在某个明确的地方被*翻译*成领域错误，否则 Handler 的 `errors.Is(err, ErrURLNotFound)` 永远匹配不上。推荐在 Repository 完成翻译：

```go
// 片段：属于 11 章项目 repository 与 service 层；import 需含 "context"、"errors"、"fmt"、"time"、"gorm.io/gorm"
var (
	ErrURLNotFound = errors.New("short url not found")
	ErrURLExpired  = errors.New("short url expired")
	ErrURLDisabled = errors.New("short url disabled")
)

// Repository：基础设施错误 → 领域错误的「翻译点」
func (r *GormURLRepo) FindByCode(ctx context.Context, code string) (*ShortURL, error) {
	var u ShortURL
	err := r.db.WithContext(ctx).Where("short_code = ?", code).First(&u).Error
	if errors.Is(err, gorm.ErrRecordNotFound) {
		return nil, ErrURLNotFound // 翻译：查无记录是预期内业务结果，不是基础设施故障
	}
	if err != nil {
		return nil, fmt.Errorf("find url by code %q: %w", code, err) // 其余错误用 %w 保留 cause
	}
	return &u, nil
}

// Service：补上过期/禁用两个领域分支
func (s *Service) Resolve(ctx context.Context, code string) (string, error) {
	u, err := s.repo.FindByCode(ctx, code)
	if err != nil {
		// %w 包装后 ErrURLNotFound 仍能被上层 errors.Is 命中
		return "", fmt.Errorf("resolve code %q: %w", code, err)
	}
	if u.Disabled {
		return "", ErrURLDisabled
	}
	if !u.ExpiresAt.IsZero() && time.Now().After(u.ExpiresAt) {
		return "", ErrURLExpired
	}
	return u.Target, nil
}
```

- 判断错误用 `errors.Is/As`，不要比较 `err.Error()` 字符串。
- `%w` 保留根因；`%v` 只生成文本，后续无法判断错误类型。
- 翻译只做一次：Repository 已经返回 `ErrURLNotFound`，Service 只负责包装与业务分支，不要再翻译第二遍。
- Repository 不认识 HTTP；Service 不返回 `gin.H`；Handler 不暴露 SQL、DSN、堆栈。

### 4.2 HTTP 错误响应只在边界映射一次

```json
{
  "code": "SHORT_URL_NOT_FOUND",
  "message": "short URL does not exist",
  "request_id": "01J..."
}
```

| 领域结果 | HTTP | 对外错误码 | 是否记录 Error 日志 |
|----------|------|------------|----------------------|
| 参数校验失败 | 400 | `INVALID_ARGUMENT` | 否，计数即可 |
| 未认证 / 无权限 | 401 / 403 | `UNAUTHORIZED` / `FORBIDDEN` | Warn（出现异常峰值时） |
| 短码不存在 | 404 | `SHORT_URL_NOT_FOUND` | 否，避免扫描流量刷屏 |
| 短码已过期 / 已禁用 | 410 | `SHORT_URL_EXPIRED` / `SHORT_URL_DISABLED` | 否，属预期业务结果 |
| 自定义短码冲突 | 409 | `SHORT_CODE_CONFLICT` | 否 |
| 限流 | 429 | `RATE_LIMITED` | 否，指标告警 |
| MySQL 等依赖超时 | 503 | `DEPENDENCY_UNAVAILABLE` | Error，保留 cause |
| 未知错误 | 500 | `INTERNAL_ERROR` | Error |

对应 §4.1 的三个领域错误，Handler 里的映射代码就是一组 `errors.Is` 分支：

```go
// 片段：Gin Handler 边界映射；import 需含 "errors"、"net/http"、"github.com/gin-gonic/gin"、"go.uber.org/zap"
func (h *Handler) Redirect(c *gin.Context) {
	target, err := h.svc.Resolve(c.Request.Context(), c.Param("code"))
	switch {
	case err == nil:
		c.Redirect(http.StatusFound, target) // 302
	case errors.Is(err, ErrURLNotFound):
		c.JSON(http.StatusNotFound, gin.H{"code": "SHORT_URL_NOT_FOUND", "message": "short URL does not exist"})
	case errors.Is(err, ErrURLExpired):
		c.JSON(http.StatusGone, gin.H{"code": "SHORT_URL_EXPIRED", "message": "short URL expired"}) // 410
	case errors.Is(err, ErrURLDisabled):
		c.JSON(http.StatusGone, gin.H{"code": "SHORT_URL_DISABLED", "message": "short URL disabled"})
	default:
		// 未预期错误：只在边界这一层记一次 Error 日志，对外不暴露内部细节
		h.logger.Error("resolve failed", zap.String("short_code", c.Param("code")), zap.Error(err))
		c.JSON(http.StatusInternalServerError, gin.H{"code": "INTERNAL_ERROR", "message": "internal error"})
	}
}
```

**原则**：预期内的业务失败不是服务故障。日志只记录一次，通常由最靠近请求边界、拥有 request ID 和业务字段的一层记录；底层负责包装，不要层层重复打印同一个错误。

### 4.3 日志字段与级别规范

| 级别 | 何时使用 | 短链示例 |
|------|----------|----------|
| Debug | 本地调试、默认生产关闭 | Base62 中间值 |
| Info | 状态变化或低频关键事件 | 服务启动、迁移版本、配置摘要（脱敏） |
| Warn | 可恢复、需要关注 | Redis 超时后降级到 MySQL、429 激增 |
| Error | 请求失败或后台任务最终失败 | MySQL 不可用、消息进入 DLQ |
| Panic/Fatal | 仅启动期无法继续 | 配置非法；业务请求中禁止使用 |

推荐公共字段：`request_id`、`route`、`method`、`status`、`latency_ms`、`error_code`；短链字段：`short_code`、`cache_result`、`event_id`。生产日志写 JSON 到 stdout，由 Docker/Loki/ELK 收集。

禁止记录：密码、Token、Cookie、完整 DSN、完整 IP、含敏感 query 的长 URL。确需分析时保存脱敏值或不可逆 hash（例如 Token 只保留前几位、DSN 隐去密码段），并定义保留周期。

### 4.4 为什么不用 fmt.Println

| fmt.Println | zap |
|-------------|-----|
| 无级别 | Debug/Info/Warn/Error |
| 难检索 | JSON 字段可 Loki/ELK 搜索 |
| 文本格式容易漂移 | 字段契约稳定，可做告警与统计 |
| 高频路径开销不可控 | 支持高性能编码与采样 |

### 4.5 初始化

dev 用 `NewDevelopmentConfig`（Console 编码，人类可读）；prod 用 `NewProductionConfig`（JSON 编码）。注意一个容易被写错的细节：**两者默认的 `OutputPaths` 都是 `["stderr"]`，不是 stdout**。容器环境里 stdout/stderr 都会被 Docker/Loki/ELK 的日志驱动采集，写哪个均可；但若团队规范要求写 stdout（如 §4.3 所述），必须显式设置 `cfg.OutputPaths = []string{"stdout"}`，不能依赖默认值。

```go
// 完整可编译清单：logging/logger.go
package logging

import (
	"fmt"

	"go.uber.org/zap"
)

// InitLogger 按环境构建 zap.Logger：dev 彩色 Console，prod JSON。
func InitLogger(env string) (*zap.Logger, error) {
	var cfg zap.Config
	switch env {
	case "prod":
		cfg = zap.NewProductionConfig() // JSON、Info 级别、采样；默认 OutputPaths 是 ["stderr"]
		cfg.OutputPaths = []string{"stdout"} // 团队规范要求 stdout 时需显式覆盖
	case "dev", "":
		cfg = zap.NewDevelopmentConfig() // Console、Debug 级别；默认同样输出 stderr
	default:
		return nil, fmt.Errorf("unknown log env %q (want dev/prod)", env)
	}
	logger, err := cfg.Build()
	if err != nil {
		return nil, fmt.Errorf("build zap logger: %w", err)
	}
	return logger, nil
}
```

`main` 中使用（`env` 取自 §5 配置的 `log.env`）：

```go
// 片段：main.go 启动段
logger, err := logging.InitLogger(cfg.Log.Env)
if err != nil {
	panic(err) // 日志都起不来，直接 fail fast
}
defer func() { _ = logger.Sync() }()
```

启动时校验日志级别；退出前调用 `Sync()`，但对 stdout/stderr 的 `invalid argument` 可按平台忽略。

### 4.6 在 Redirect Handler 中使用

Redirect 请求不建议每次都打成功 Info 日志，否则高 QPS 下日志成本可能比业务还高。更合适的策略是：

- 成功量、延迟、缓存命中放 Prometheus；日志只采样或在 Debug 输出。
- 失败打带 `request_id`、`short_code`、`error_code`、`latency_ms` 的结构化日志。
- Redis 降级只在状态切换或采样后记录 Warn，避免同一故障每秒打印数万行。
- 异步统计对接 08 章设计时约定事件日志：Redirect 侧入队成功打 `stat_enqueued`，消费者落库后打 `stat_persisted`，两条日志携带同一个 `event_id`，便于定位重复、重试和 DLQ。

### 4.7 标准库 log/slog：零依赖的另一条主线

Go 1.21 引入的 `log/slog` 是标准库结构化日志，到本章基线的 Go 1.26 已稳定多年，2026 年的新项目里它和 zap 同为主流选择，面试同样会问。最小可运行示例：

```go
// 完整可编译清单：slog 最小示例（独立 main.go）
package main

import (
	"context"
	"log/slog"
	"os"
)

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
		Level: slog.LevelInfo,
	}))
	slog.SetDefault(logger) // 之后包级 slog.Info 等都走这个 JSON handler

	slog.Info("service started", "addr", ":8080", "env", "prod") // key-value 交替
	slog.Warn("redis timeout, fallback to mysql",
		slog.String("cache_result", "error"), slog.Int("attempt", 2)) // 强类型 Attr 写法

	// 与 context 结合：InfoContext 把 ctx 传给 Handler，
	// 自定义 Handler 可从 ctx 中提取 request_id/trace_id 附加到每条日志
	ctx := context.Background()
	slog.InfoContext(ctx, "redirect ok", slog.String("route", "/:code"), slog.Int("status", 302))
}
```

选型对照（本章主线仍用 zap，理由见下表）：

| 维度 | zap | log/slog |
|------|-----|----------|
| 依赖 | 第三方 `go.uber.org/zap` | 标准库（Go 1.21+），零依赖 |
| 性能 | 极致（零分配编码器、内置采样） | 足够好；极高 QPS 热点路径略逊 |
| 生态 | 成熟，中间件/库适配多，面试常见 | 标准接口，新库逐渐原生支持 |
| API | 强类型 `zap.String/Int` | key-value 交替或 `slog.Attr` 均可 |
| 适合 | 高 QPS 服务、团队已有 zap 规范 | 新项目、写库/SDK、想减少依赖 |

**建议**：已有项目跟随团队现状；新项目可直接用 slog；无论选哪个，§4.3 的字段与级别规范同样适用。

### 4.8 request_id 贯穿一次请求：logger 随 context 传递

§4.3 要求日志携带 `request_id`，但不能让每个函数多一个 `logger` 参数。惯用模式：中间件生成 `request_id` → 构造带字段的 logger → 放进 `context` → 下层随取随用。

```go
// 完整可编译清单：logging/ctx.go（同 §4.5 的 logging 包）
package logging

import (
	"context"

	"github.com/gin-gonic/gin"
	"github.com/google/uuid"
	"go.uber.org/zap"
)

type ctxKey struct{}

// WithLogger 把带字段的 logger 放进 context。
func WithLogger(ctx context.Context, l *zap.Logger) context.Context {
	return context.WithValue(ctx, ctxKey{}, l)
}

// FromContext 下层取出 logger；取不到时退回全局 logger，避免 nil panic。
func FromContext(ctx context.Context) *zap.Logger {
	if l, ok := ctx.Value(ctxKey{}).(*zap.Logger); ok {
		return l
	}
	return zap.L()
}

// RequestIDMiddleware 生成/透传 request_id，并注入带字段的 logger。
func RequestIDMiddleware(base *zap.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		requestID := c.GetHeader("X-Request-ID") // 网关已生成则透传
		if requestID == "" {
			requestID = uuid.NewString()
		}
		c.Writer.Header().Set("X-Request-ID", requestID) // 回传给客户端便于报障
		l := base.With(zap.String("request_id", requestID))
		c.Request = c.Request.WithContext(WithLogger(c.Request.Context(), l))
		c.Next()
	}
}
```

下层（Service/Repository）不再接收 logger 参数，直接 `logging.FromContext(ctx).Warn("cache miss fallback", zap.String("short_code", code))`——这条日志自动带上 `request_id`。

**怎么在单元测试里断言“日志真的打了、字段真的对”**：用 zap 自带的 `observer`（内存 core，记录每条 entry）：

```go
// 片段：属于任意 xxx_test.go；import 需含 "testing"、"go.uber.org/zap"、"go.uber.org/zap/zaptest/observer"
func TestLogCarriesRequestID(t *testing.T) {
	core, logs := observer.New(zap.WarnLevel) // 只捕获 Warn 及以上
	logger := zap.New(core).With(zap.String("request_id", "req-123"))

	logger.Warn("redis timeout, fallback to mysql")

	entries := logs.FilterMessage("redis timeout, fallback to mysql").All()
	if len(entries) != 1 {
		t.Fatalf("want 1 log entry, got %d", len(entries))
	}
	if got := entries[0].ContextMap()["request_id"]; got != "req-123" {
		t.Fatalf("request_id = %v, want req-123", got)
	}
}
```

日常业务测试不必逐条断言日志；但「降级必须打 Warn」「错误日志必须带 request_id」这类**日志契约**值得用 observer 锁住，防止重构时悄悄丢字段。

### 5.2 加载：LoadConfig 完整实现

核心链路：`SetConfigFile` → `SetEnvPrefix("APP")` → `SetEnvKeyReplacer` → `AutomaticEnv` → `ReadInConfig` → `Unmarshal` 到带 `mapstructure` tag 的强类型 struct。环境变量按 `APP_MYSQL_DSN` 覆盖 `mysql.dsn`；Docker 13 章通过 secret 或环境变量注入。

```go
// 完整可编译清单：config/config.go
package config

import (
	"fmt"
	"strings"
	"time"

	"github.com/spf13/viper"
)

// 字段与 §5.1 的 yaml 一一对应；tag 名是 mapstructure（viper 用它解码），不是 json/yaml
type Config struct {
	Server ServerConfig `mapstructure:"server"`
	MySQL  MySQLConfig  `mapstructure:"mysql"`
	Redis  RedisConfig  `mapstructure:"redis"`
	Log    LogConfig    `mapstructure:"log"`
}

type ServerConfig struct {
	Addr            string        `mapstructure:"addr"`
	ShutdownTimeout time.Duration `mapstructure:"shutdown_timeout"` // "10s" 自动解码成 time.Duration
}

type MySQLConfig struct {
	DSN string `mapstructure:"dsn"`
}

type RedisConfig struct {
	Addr string `mapstructure:"addr"`
	DB   int    `mapstructure:"db"`
}

type LogConfig struct {
	Level string `mapstructure:"level"`
	Env   string `mapstructure:"env"`
}

func LoadConfig(path string) (*Config, error) {
	v := viper.New()
	v.SetConfigFile(path)

	v.SetEnvPrefix("APP")                              // 环境变量统一前缀 APP_
	v.SetEnvKeyReplacer(strings.NewReplacer(".", "_")) // mysql.dsn → APP_MYSQL_DSN
	v.AutomaticEnv()                                   // 读键时自动查同名环境变量

	// 著名的坑：AutomaticEnv 只对 viper「已知」的键生效。yaml 里不存在的键，
	// 即使设置了 APP_XXX 环境变量，Unmarshal 也读不进来——必须先用
	// SetDefault 或 BindEnv 把键注册进 viper。
	v.SetDefault("server.addr", ":8080")
	v.SetDefault("server.shutdown_timeout", "10s")
	if err := v.BindEnv("mysql.dsn"); err != nil { // 显式绑定：保证 APP_MYSQL_DSN 一定可见
		return nil, fmt.Errorf("bind env mysql.dsn: %w", err)
	}

	if err := v.ReadInConfig(); err != nil {
		return nil, fmt.Errorf("read config %s: %w", path, err)
	}

	var cfg Config
	if err := v.Unmarshal(&cfg); err != nil {
		return nil, fmt.Errorf("unmarshal config: %w", err)
	}

	// 显式校验：fail fast，不把坏配置带进运行期
	if cfg.MySQL.DSN == "" {
		return nil, fmt.Errorf("mysql.dsn is required (set it in %s or via APP_MYSQL_DSN)", path)
	}
	if cfg.Server.ShutdownTimeout <= 0 {
		return nil, fmt.Errorf("server.shutdown_timeout must be > 0, got %s", cfg.Server.ShutdownTimeout)
	}
	return &cfg, nil
}
```

本机（Windows PowerShell）验证环境变量覆盖：

```powershell
$env:APP_SERVER_ADDR = ":9090"
go run . -config .\config\config.dev.yaml   # 应监听 9090
Remove-Item Env:APP_SERVER_ADDR             # 用完清理，避免影响后续测试
```

Linux 服务器/容器里对应 `export APP_SERVER_ADDR=:9090`。

配置加载后必须做显式校验：端口是否合法、超时是否大于 0、MySQL DSN 是否存在、生产环境是否误用了默认密码。日志只打印“加载来源和非敏感摘要”，不打印完整配置对象。

命令行 flag 与 viper 不是二选一而是并存：flag 只负责选择配置文件路径（如 `-config ./config/config.prod.yaml`），文件内容解析与环境变量覆盖交给 viper（§8 练习 L2 会实作这个模式）。

### 5.4 版本化数据库迁移：禁止生产靠 AutoMigrate

开发期 `AutoMigrate` 很方便，但它无法清楚表达数据回填、索引创建顺序和回滚策略。简历项目推荐选择一种工具并固定下来：`golang-migrate/migrate` 或 `pressly/goose`。

```text
migrations/
├── 000001_create_short_urls.up.sql
├── 000001_create_short_urls.down.sql
├── 000002_add_expire_and_status.up.sql
├── 000002_add_expire_and_status.down.sql
├── 000003_create_click_event_dedup.up.sql
└── 000003_create_click_event_dedup.down.sql
```

命名规则是“单调递增版本 + 动作”；已在共享环境执行过的文件**不允许原地修改**，发现遗漏就增加新版本。工具会维护 schema version 表，回答“这个环境现在执行到哪一版”。

```bash
# 示例：命令行工具的参数以你最终选择的 migrate/goose 为准
migrate -path ./migrations -database "$DATABASE_URL" version
migrate -path ./migrations -database "$DATABASE_URL" up
```

### 5.5 发布时的迁移流程

```text
备份/确认可恢复
   → CI 在空库执行 up
   → CI 从上一发布版本执行 up
   → 单独 migration job 执行一次
   → 检查 schema version
   → 启动新 App
   → readiness + E2E smoke test
```

- 不让多个 App 副本在启动时同时抢着迁移；迁移是独立、一次性的发布步骤。
- 使用 **Expand → Migrate Data → Contract**：先加兼容字段/表，再让新旧代码都能运行，最后一个发布周期后删除旧字段。
- 大表加索引要评估锁表时间，必要时使用在线 DDL；迁移设置超时并监控。
- `down` 不是万能回滚。删除列等破坏性操作可能无法恢复数据，生产回滚通常优先回滚镜像，并依赖向后兼容 schema。
- `force version` 只能在人工确认数据库真实状态后使用，不能作为“迁移失败就强行跳过”的脚本。

### 5.6 migration 最小验收

| 场景 | 必须验证 |
|------|----------|
| 全新环境 | 从空库 `up` 到最新版，服务能创建并跳转短链 |
| 版本升级 | 从上一发布版本数据升级，旧数据仍可读取 |
| 重复执行 | 再次 `up` 不重复建表、不破坏数据 |
| 失败恢复 | 脚本失败时能定位版本，按 runbook 修复而非删库重来 |
| 回滚演练 | 在可逆迁移上验证 `down`；破坏性迁移验证备份恢复 |

## 6. 优雅停机（Graceful Shutdown）

**术语（Graceful Shutdown）**：收到终止信号后，停止接收新请求，等待在途请求完成再退出。
**生活类比**：餐厅打烊——不再接新客，但要把已点的菜做完。
**为什么重要**：K8s/Docker 滚动更新先发 SIGTERM；直接 kill 会导致 302 中断、MQ 统计重复或丢失。

下面是完整最小骨架，三个要点都不能省：**ListenAndServe 必须放 goroutine**（否则永远执行不到等信号的那一行）、**`http.ErrServerClosed` 不是故障**（Shutdown 后 ListenAndServe 必然返回它）、**Shutdown 的错误必须处理**（超时返回 `context.DeadlineExceeded`，说明有在途请求被强制中断——这正是最需要记日志/打指标的时刻，对应 §7.5 的 `shutdown_phase` 字段与 shutdown duration 指标）。

```go
// 完整可编译清单：优雅停机最小骨架（main.go）
package main

import (
	"context"
	"errors"
	"net/http"
	"os/signal"
	"syscall"
	"time"

	"github.com/gin-gonic/gin"
	"go.uber.org/zap"
)

func main() {
	logger, err := zap.NewProduction()
	if err != nil {
		panic(err)
	}
	defer func() { _ = logger.Sync() }()

	r := gin.New()
	r.GET("/healthz", func(c *gin.Context) { c.JSON(http.StatusOK, gin.H{"status": "ok"}) })
	srv := &http.Server{Addr: ":8080", Handler: r} // Gin 的 r 就是一个 http.Handler

	// Go 1.16+ 的现代写法：NotifyContext 代替手写 quit channel，信号到来时 ctx 被取消
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	// 要点 1：ListenAndServe 放 goroutine，主流程才能走到下面的 select 等信号
	serveErr := make(chan error, 1)
	go func() {
		// 要点 2：Shutdown 后 ListenAndServe 一定返回 http.ErrServerClosed，不加判断会被误当成启动失败
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			serveErr <- err
		}
		close(serveErr)
	}()

	select {
	case err := <-serveErr: // 端口被占等真正的启动失败
		logger.Fatal("server failed to start", zap.Error(err))
	case <-ctx.Done(): // 收到 SIGINT/SIGTERM，开始打烊
	}

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second) // 生产从 cfg.Server.ShutdownTimeout 读
	defer cancel()
	// 要点 3：不丢弃 Shutdown 的返回值
	if err := srv.Shutdown(shutdownCtx); err != nil {
		logger.Error("graceful shutdown timeout, in-flight requests aborted",
			zap.Error(err), zap.String("shutdown_phase", "http_drain"))
	} else {
		logger.Info("server exited cleanly", zap.String("shutdown_phase", "done"))
	}
	<-serveErr // 等 serve goroutine 真正退出，再做后续清理
}
```

| 关键行 | 含义 | 改错会怎样 |
|------|------|------------|
| `signal.NotifyContext` | 注册 SIGINT/SIGTERM，信号即取消 ctx | 收不到 Docker stop 信号，只能被 kill -9 |
| `go srv.ListenAndServe()` | 监听放后台，主流程等信号 | 同步调用会阻塞，永远走不到等信号处 |
| `!errors.Is(err, http.ErrServerClosed)` | 区分「正常关闭」与「启动失败」 | 每次正常停机都误报 Fatal |
| `Shutdown(shutdownCtx)` | 关闭 listener + 等待 handler | 超时后强杀可能丢请求 |
| `WithTimeout` | 最长等待 10s | 无限等待导致部署卡住 |
| `if err := srv.Shutdown(...)` | 超时被强制中断的请求要留下证据 | `_ =` 丢弃后线上丢请求无从追查 |

**完整闭环：HTTP 排空只是第一步**。真实服务停机要按依赖方向逆序关闭：

```text
收到 SIGTERM
  → readiness 探针返回失败，负载均衡/K8s 摘除新流量
  → srv.Shutdown 排空在途 HTTP 请求
  → 停 MQ consumer：处理完手头消息再 Close（对应 08 章异步统计）
  → flush 统计缓冲、关闭 producer
  → 关闭 DB/Redis 连接池（sqlDB.Close() / rdb.Close()）
  → logger.Sync()，进程退出
```

- 等 serve goroutine 真正退出：用上面的 done/err channel，或 `golang.org/x/sync/errgroup`——`g.Go` 分别跑 serve 与信号监听，`g.Wait()` 统一收尾。
- `srv.RegisterOnShutdown(f)` 注册的回调会在 Shutdown 开始时并发执行，适合通知内部组件「开始打烊」（如主动断开长连接/WebSocket）。
- 后台 worker（14 章 MQ 消费者）要有自己的 ctx：主流程 cancel 后按上表顺序 Close，避免 HTTP 已停、统计还在写库。

## 7. 可观测性、E2E 与 CI 质量门禁

### 7.1 Prometheus：先做 RED，再做业务指标

RED 是 HTTP 服务最小观测面：

- **Rate**：每秒请求数。
- **Errors**：错误数/错误率。
- **Duration**：延迟分布，重点看 P95/P99，而不是只看平均值。

推荐指标名与标签：

| 指标 | 类型 | 低基数标签 | 回答的问题 |
|------|------|------------|------------|
| `http_requests_total` | Counter | `route,method,status` | 流量和错误率是否异常 |
| `http_request_duration_seconds` | Histogram | `route,method` | P95/P99 是否退化 |
| `http_in_flight_requests` | Gauge | `route` | 是否出现拥塞 |
| `shorturl_redirect_total` | Counter | `result,cache_result` | 跳转成功、过期、禁用、缓存命中情况 |
| `shorturl_create_total` | Counter | `result` | 创建成功、冲突、限流情况 |
| `click_event_total` | Counter | `stage,result` | publish/consume/retry/dlq 是否健康 |
| `click_consumer_lag` | Gauge | `consumer_group` | 点击统计是否积压 |

**命名说明**：表中 `http_*` 通用指标在代码里通过 `Namespace: "shorturl"` 自动加前缀，`/metrics` 输出的完整指标名是 `shorturl_http_requests_total`、`shorturl_http_request_duration_seconds` 等，PromQL 也必须按完整名（带前缀）查询；表中已自带 `shorturl_`/`click_` 前缀的业务指标则在定义时直接写全名、不再设置 Namespace，避免出现 `shorturl_shorturl_...` 双前缀。

**标签红线**：不能把 `short_code`、`user_id`、IP、完整 URL、`request_id/event_id` 放进 Prometheus label。这些值近乎无限，会造成高基数和内存爆炸；单次定位放日志，聚合趋势放指标。

```go
// 片段：metrics.go；import 需含 "github.com/prometheus/client_golang/prometheus"
// 和 "github.com/prometheus/client_golang/prometheus/promauto"
//
// 注意：不注册的指标不会出现在 /metrics 里，而且没有任何报错，极难排查。
// promauto.NewHistogramVec 会自动注册到默认 Registry；
// 若坚持用 prometheus.NewHistogramVec，必须补 prometheus.MustRegister(requestDuration)。
var requestDuration = promauto.NewHistogramVec(
    prometheus.HistogramOpts{
        Namespace: "shorturl", // 最终指标名：shorturl_http_request_duration_seconds
        Name:      "http_request_duration_seconds",
        Help:      "HTTP request latency in seconds.",
        Buckets:   []float64{.005, .01, .025, .05, .1, .25, .5, 1},
    },
    []string{"route", "method"},
)
```

指标定义了还要真的「观测」——在 Gin 中间件里于 `c.Next()` 之后打点：

```go
// 片段：middleware.go；import 需含 "time"、"github.com/gin-gonic/gin"
func MetricsMiddleware() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()
		route := c.FullPath() // 路由模板 /:code，而不是原始 URL
		if route == "" {
			route = "unmatched" // 404 等未匹配请求归入固定值，避免高基数
		}
		requestDuration.WithLabelValues(route, c.Request.Method).
			Observe(time.Since(start).Seconds())
	}
}
```

Gin 中间件在 `c.Next()` 后使用路由模板 `c.FullPath()`，不要用原始 URL（`/abc1`、`/abc2` 会制造新 label）。`/metrics` 使用 `promhttp.Handler()` 暴露，并在生产网络层限制访问。

常用 PromQL 思路：

```promql
# 某路由 P95
histogram_quantile(0.95,
  sum by (le, route) (rate(shorturl_http_request_duration_seconds_bucket[5m])))

# 5 分钟 5xx 比例
sum(rate(shorturl_http_requests_total{status=~"5.."}[5m]))
/
sum(rate(shorturl_http_requests_total[5m]))
```

告警应面向用户影响：持续 5 分钟错误率超阈值、P99 超 SLO、消费者积压持续增长。不要因一次瞬时尖峰半夜叫醒人；阈值必须由真实压测和运行基线校准。

#### 7.1.1 第三支柱：链路追踪（tracing）最小指引

§1 说可观测性有三支柱：日志、指标、链路追踪。本章落地了前两柱；第三柱先建立最小认知，本教程不展开实战：

- **是什么**：一次请求跨 Gin → Service → MySQL/Redis → MQ 的完整调用链；每一跳是一个 span，同一条链共享一个 `trace_id`，能直接回答「这次慢在了哪一跳」。
- **用什么**：Go 生态的事实标准是 OpenTelemetry（`go.opentelemetry.io/otel`）。`otelgin` 中间件自动为每个 HTTP 请求建 span，存储层有 `otelgorm`、go-redis v9 的 `redisotel` 等仪表化包，后端常配 Jaeger/Tempo 查看。
- **与日志打通**：把 `trace_id` 像 §4.8 的 `request_id` 一样放进日志字段（同样通过 context 传递），排障时先用 trace 定位慢的那一跳，再用 trace_id 捞对应日志。
- **何时值得上**：单体短链服务里日志 + 指标基本够用；服务拆分、跨服务调用（如 14 章的分布式场景）后 tracing 价值最大。面试被问「三支柱」时，至少能说出以上分工。

### 7.2 测试分层

| 层级 | 是否连真实依赖 | 短链项目覆盖 | 运行位置 |
|------|----------------|--------------|----------|
| 单元测试 | 否 | Base62、过期/禁用判断、Service 分支 | 每次保存/PR |
| Handler/组件测试 | 否或 fake | JSON 契约、HTTP 状态、错误码 | PR |
| 集成测试 | Testcontainers 真 MySQL/Redis | Repository、缓存一致性、migration | PR |
| E2E | 完整 Compose | 创建→查询→302→统计最终落库 | PR 或主分支 |
| 故障测试 | 主动停依赖/注入超时 | Redis/MySQL/MQ 降级与恢复 | 主分支/发布前 |

层级之间的数量关系遵循测试金字塔：单元测试最多、运行最快，每次保存都能跑；集成测试只挑 5～10 条关键路径（Repository 读写、缓存一致性、migration 升级），不要试图用集成测试覆盖所有业务分支——那是单元测试的职责。

E2E 不只验证“返回 200”：

1. 从空库执行 migration。
2. 创建带过期时间的短链，断言响应 schema。
3. 第一次跳转走 DB，第二次命中 Redis，均校验 `Location`。
4. 禁用后缓存失效，跳转返回约定状态。
5. 重复 `event_id` 被消费者处理时，PV 只增加一次。
6. 服务收到 SIGTERM 后不接新流量，并在超时内排空。

### 7.3 故障测试：验证你声称的降级能力

| 注入故障 | 预期行为 | 必查证据 |
|----------|----------|----------|
| 停 Redis | Redirect 回源 MySQL；不能把依赖失败误判成 404 | Warn 采样、cache error 指标、错误率 |
| 停 MySQL | 已缓存链接仍可跳转；cache miss 返回 503 | readiness、5xx、连接池指标 |
| 停 MQ/Stream | 跳转优先可用；统计按 14 章策略重试/降级 | publish error、fallback/drop、告警 |
| 注入慢 DB | context 超时生效，不无限卡住 goroutine | P99、timeout error、in-flight |
| 重复投递消息 | `event_id` 唯一约束阻止重复计数 | 去重表、PV 结果、ack 日志 |

测试结束必须自动恢复依赖并清理数据。故障测试不要直接连生产；本地/CI 用独立网络、独立数据库和可重复脚本。

**注意（软依赖与 readiness）**：Redis 故障时不应让健康检查立刻把 App 摘下线——既然设计上允许回源 MySQL，Redis 就是软依赖，仅因它故障就让 readiness 失败会把仍然可用的实例摘掉、反而放大故障。正确做法是靠降级指标与告警跟进，故障期间接受性能退化；依赖分级矩阵见 14 章。

### 7.4 PR 的 CI 门禁

建议按“快反馈在前、昂贵检查在后”排列：

```text
gofmt 检查
  → go vet / staticcheck
  → 单元与 Handler 测试
  → go test -race ./...
  → 生成 coverage
  → migration 空库/升级测试
  → MySQL + Redis 集成测试
  → Compose E2E
  → docker build
```

可直接执行的基础命令（CI/Linux shell 写法；本机 PowerShell 里 `gofmt -l .` 输出为空即通过）：

```bash
# Linux CI 环境
test -z "$(gofmt -l .)"
go vet ./...
go test -race -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

实际工程的 CI 里，格式与静态检查通常不逐个跑，而是用 **golangci-lint**（linter 聚合器，CI 事实标准）一次执行几十个 linter：

```powershell
golangci-lint run ./...
```

`.golangci.yml` 最小配置——先开少量高价值 linter，别一上来全量开启把自己淹没在告警里：

```yaml
# .golangci.yml
linters:
  enable:
    - govet
    - staticcheck
    - errcheck      # 抓漏掉的 err 检查——Go 项目最常见的隐性 bug 来源
    - ineffassign
    - misspell
```

「工具在 CI 固定版本」怎么落地？Go 1.24+ 给了官方答案：**`go.mod` 的 `tool` 指令**，把 CLI 工具当作依赖记录并锁定版本，团队与 CI 天然一致：

```powershell
# 把工具记录进 go.mod 的 tool 指令并锁定版本
go get -tool golang.org/x/vuln/cmd/govulncheck@v1.1.4
go get -tool honnef.co/go/tools/cmd/staticcheck@2025.1

# 运行时加 go tool 前缀，自动使用 go.mod 锁定的版本
go tool govulncheck ./...
go tool staticcheck ./...
```

golangci-lint 官方更推荐用发布的二进制安装；在 GitHub Actions 中用 `golangci/golangci-lint-action` 并显式写死 `version:`，效果等同于版本固定。

- 核心 domain/service 包可设 75%～85% 的覆盖率门槛；不要为了全仓 100% 给生成代码写无意义测试。覆盖率只是门槛之一：优先覆盖领域规则、错误分支、并发与历史 bug，它不能替代有效断言和 E2E。
- `-race` 在 CI 每次 PR 必跑；本地改动并发代码后也应先 `go test -race ./...` 再提交，不要把竞态留到 CI 才发现。
- `golangci-lint`、`staticcheck`、`govulncheck` 等工具在 CI 固定版本（tool 指令或 Action 写死版本号），避免“latest 今天突然破坏构建”。
- PR 必须通过所有 required checks 才能合并；主分支构建不可变的 commit-SHA 镜像，13 章再负责部署。
- 覆盖率下降、race、migration 失败、E2E 失败都应阻止合并，不能用“重跑直到绿”掩盖 flaky test。

### 7.5 与短链项目的工程化验收清单

| 模块 | 自动测试 | 日志关键字段 | 指标/配置 |
|------|----------|--------------|-----------|
| Base62 / 发号 | 边界、并发、唯一索引冲突 | `error_code` | 冲突数；`id.worker_id`（若使用雪花） |
| Create API | mock repo + 真 DB + 幂等 case | `request_id, user_id_hash` | `create_total{result}`、DB timeout |
| Redirect 302 | cache miss/hit、过期、禁用、依赖故障 | `request_id, short_code, cache_result` | RED、`redirect_total`、cache hit ratio |
| 统计投递/消费 | 重复、重试、DLQ、批量落库 | `event_id, stage, attempt` | publish/consume error、lag、DLQ |
| migration | 空库、上一版本升级、失败恢复 | `from_version,to_version` | `schema_version` |
| Shutdown | 在途请求、后台 worker drain | `shutdown_phase` | shutdown duration |

做到这里，项目展示的不再是“我会用几个库”，而是：有错误契约、有可观测证据、有自动化质量门禁，并且真的演练过依赖故障。

## 9. 常见报错表

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `go test` 找不到测试 | 文件非 `_test.go` 或函数非 `Test` 前缀 | 改命名 |
| 测试访问真实 DB | 未 mock 接口 | 抽 interface |
| zap 无输出 | 级别过高 / logger 用了 `zap.NewNop` / `OutputPaths` 配置错误 | dev 用 DevelopmentConfig；核对级别与输出路径 |
| viper 读不到 env | 前缀或 Replacer 错 | 打印 `v.AllSettings()` |
| migration 显示 dirty | SQL 执行到一半失败 | 停止发布，确认实际 schema 后修复；不要盲目 force |
| `/metrics` 内存持续涨 | label 放了 code/IP/URL | 只保留 route/result 等有限枚举 |
| CI 偶发失败 | 测试共享端口/全局状态/固定 sleep | 隔离资源、轮询 readiness、消除竞态 |
| E2E 把 Redis 故障当 404 | 把 cache error 当 cache miss | 区分 miss 与 dependency error，回源或 503 |
| Shutdown 超时 | handler 阻塞无 ctx | handler 传 `r.Context()` |
| 竞态 FAIL | 共享 map 无锁 | `-race` 定位 + mutex |

> 注：漏调 `Sync()` **不会**导致「看不到输出」——zap 默认配置写 stdout/stderr 时不做用户态缓冲，每条日志立即写出。`Sync` 只在使用 `zapcore.BufferedWriteSyncer`、写文件等缓冲场景下才影响落盘，以及进程退出前作为兜底调用；排查“无输出”时不要往这个方向找。
